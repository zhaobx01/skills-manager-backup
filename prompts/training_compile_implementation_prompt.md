# 实施并验证 Compile 优化

使用 `torch-compile-integration` Skill，根据已有分析报告，以最小、可回退的方式接入并验证 `torch.compile`。遵循 Skill 的实施与验证规范，按需使用相关诊断 Skill；不重复展开已有且仍有效的分析，不扩展到其他优化。

## 硬性底线

- 新增编译默认关闭，可回退；已有编译单独记录。
- 先正确性、后性能；诊断性例外须明确授权。
- 先导运行后冻结正式协议，先导数据不进入有效统计。
- 无效轮次保留，不事后删慢步或混用不同协议。
- 不自动扩大预算，不停止其他用户任务。

## 输入与关键决策

- 项目路径：【默认当前项目】
- 分析报告：【路径】
- 运行环境与启动命令：【已知则填写，否则从项目记录核实】
- 优化目标：【吞吐／总训练耗时／峰值显存／首步延迟，注明优先级】
- 测试资源与预算：【设备、累计时间、空闲判据、单任务超时、资源等待上限及超时/干扰处理方式；未明确时先询问】
- 验收要求：【项目已有数值容差、收益与显存门槛；未知则提出建议并确认】
- 输出目录：【独立新目录；未指定时使用带时间戳的目录】

使用 `grill-me` 确认无法从现有材料核实、且会改变实施或验收方案的关键决策。普通可逆接入按已确认方案推进。改变计算语义、cache 行为、精度、数值容差、编译边界或测试预算前再次询问，不为追求通过而擅自调整。

先完成可在 CPU 上进行的准备，再集中确认设备阶段。一次授权可覆盖整份测试清单，包括正确性、先导运行、协议选择规则、正式测速、基线锚点及失败处理；满足约定门槛后直接启动，不逐轮重复询问。若准备本身需要改变上述关键约束，仍须先确认。

执行顺序：CPU 单测与编排 dry-run → 一次授权 → 设备正确性短训（同时采集诊断日志）→ 4.1 捕获诊断与必要修复 → 4.2 先导运行（仅 recompiles 日志）→ 冻结正式协议 → 4.3 正式测速（含 baseline 锚点）→ 4.5 按需专项（显存异常随时触发，时间线对照在测速后）→ 汇总。目标设备局部正确性检查在短训前完成；诊断日志与 Profiler 不混入正式计时。

启动门槛须在授权时明确。例如 GR00T 的 DTK 环境可参考：全部目标卡可访问、显存占用 ≤15%、利用率 ≤5%、无外部或不可归属的正显存 KFD 分配，单任务超时 1200 秒；这些是项目示例，不是通用默认值。其他平台使用适用的资源与进程归属检查，不强制要求 KFD。

未另行约定时采用保守停止策略：等待超时不启动；运行中确认外部干扰时安全终止本次任务，标为受干扰并暂停后续，不自动重试。单任务超时记为 `timeout`，保留诊断数据但不计入有效性能统计。

## 一、核实与冻结基线

1. 读取项目 `AGENTS.md`、相关 Skill、分析报告和已有实验记录，对照当前源码及有效配置，核实实际调用链、模型类型、参数冻结、精度、分布式包装、权重加载与保存路径。记录实际 Python、PyTorch、后端和硬件，不从版本名称推断目标后端已验证。
2. 明确已有编译与本轮新增编译的范围。选择证据充分的首个候选，一次只验证一个；逐块与子系统整体作为独立方案，不同时叠加父子包装。证据不足时允许暂缓实施。
3. 记录 Git SHA、tracked diff、新增实现文件及行为相关源码哈希，备份将修改的文件，保留用户已有改动和冻结源码副本，保存 `vs-baseline.diff`。默认在行为源码变化后停止串联比较；例外须有明确的文件/差异白名单、关闭路径等价的证据和用户确认，不能仅凭“新增项默认关闭”认定等价。超出白名单则停止并决定是否重建基线。
   采用白名单例外时，A-B-A 锚点中至少一个 baseline 必须在新源码上关闭新增编译后运行，并与旧 baseline 在同配置、同口径下比较。差异未超出预先确定的波动/漂移门槛，只支持“未观察到明显性能变化”，不单独证明数值或行为等价；仍需关闭路径回归。若差异超出门槛或无法判断，暂停混用历史数据，分析原因或在新源码上重建对照。
4. 固定原始 checkpoint、数据与采样顺序、种子、batch、梯度累积、AMP、学习率、优化器、分布式配置、worker 和注意力后端。显式设置当前源码支持的相关编译开关，不向旧源码强传不存在的参数；以有效配置与运行元数据自动校验实际行为，不依赖继承环境或未核实的默认值。

## 二、最小接入与回退

- 优先复用项目配置系统，在适合的初始化阶段集中安装，新增能力默认关闭，支持单项启用；单项验证后再按需组合消融，不穷举所有组合。
- 使用目标版本支持的编译入口，保留模块、参数及保存协议。先预检全部目标的类型、实例路径、数量、唯一性和已有包装，再安装；记录实际路径、数量、mode、dynamic、fullgraph 及其默认来源。
- 枚举会包装或替换目标 `forward` 的机制，包括框架输出/hidden-state 捕获、hook、monkey patch、分布式包装及 cache；明确编译点在其内侧还是外侧。检查实例属性、layer index、输入状态等 guard 差异，不能从相同层类型推断所有实例共享一张图。以实际捕获和预先解释的图数范围检查异常增长，不强制唯一图数为一。
- 默认使用 `mode="max-autotune-no-cudagraphs"`，通过 `mode` 参数修改；`mode` 与 `options` 互斥，不同时指定。启动前核实目标版本与后端支持，将 autotune 成本纳入预算；不支持或编译失败时明确报错，不静默切换模式。
- `fullgraph=False`、dynamic 保持默认行为，除非已有证据或项目要求支持其他设置。不统一强制动态形状或全图，不预先重构计算。
- 同配置重复接入应幂等；配置切换使用新进程。部分安装失败须明确标记进程不可复用，要求重启，不手动清空 PyTorch 内部状态或静默回退。
- 明确关闭路径：是原实现、重构后 eager，还是仅关闭新增编译而保留已有编译。不要将最后一种称为全模型 eager。
- 覆盖参数身份、冻结状态、train/eval、state_dict 键和重载行为。若接入影响 deepcopy、序列化、hook 或缓存，明确限制并验证实际使用路径，不以能保存权重证明所有对象序列化均受支持。

## 三、先验证控制与正确性

1. 先补回归用例，再实现接入。CPU 测试覆盖开关传递、准确匹配、隔离与组合、互斥、重复安装、失败状态和保存键；替身或 CPU `backend="eager"` 只证明接入与捕获行为，不证明目标设备 Inductor 正确性。目标版本支持时可启用重编译上限失败选项（如 `fail_on_recompile_limit_hit`），并检查相关计数器的合理上界；说明计数器范围、重置与含义。这不替代目标设备实测，也不擅自调高上限。
2. 局部对照使用相同权重、输入、状态及上游梯度，比较返回结构、输出、输入和参数梯度，报告约定容差与相对 L2 误差。合成数据通过后仍需代表性真实激活；合成数据失败时先定位，不能直接认定真实训练必然失败。
3. 确定性局部测试可隔离 dropout，但实际短训保留训练随机性。覆盖真实 shape、长度、padding、mask 与状态变化；不要求随机训练轨迹逐位一致，也不以随机性为由忽略明显偏差。
4. 在目标设备上运行同条件的独立进程短训，检查原始 loss、有效掩码、非零有效梯度、优化器状态、更新后参数均有限，并确认参数实际更新。数值异常时各 rank 在一致边界退出，禁止继续更新或保存异常模型。短训同时开启目标版本支持的 `TORCH_LOGS="graph_breaks,recompiles"` 和 `TORCH_TRACE`，作为 4.1 捕获诊断的主要数据。短训带数值检查 hook，可能改变图断与 guard，其证据只代表“带检查路径”；关闭检查后的实际编译行为由 4.2 核实。短训耗时不用于性能结论。
5. 按预算验证正常模型保存、完整权重扫描、离线重载与真实输入预测。进程退出、日志 loss 有限、保存成功或单个参数抽查，都不替代完整验收。
6. 需要计算重构时，分别比较 A 原实现、B 重构后 eager、C 重构后 compile；B/C 才用于归因纯编译收益。cache、hook 或布局调整单独列项，不默认视为无算法影响。

正确性失败按文首底线处理；获准继续的诊断性测速须始终保留“正确性未通过”标记。

## 四、独立采集与正式测速

### 4.1 捕获与重编译诊断

1. **核实与采集。** 以 3.4 短训开启的 `TORCH_LOGS="graph_breaks,recompiles"` 与 `TORCH_TRACE` 为主要数据，在已有工具环境中解析 tlparse 报告；也可使用可关联当前源码、配置和编译范围的已有日志。记录完整命令、有效配置、版本、缓存状态和各 rank 日志，确保变量未被启动脚本取消、输出不相互覆盖。覆盖真实形状、训练状态和前向/反向；短训步数通常不足以覆盖后段形状，后段重编译由 4.2 先导补充。不得仅因缺日志自动扩大预算或安装工具。
2. **定位与归类。** 使用 `debug-graph-breaks` 结合源码、实际调用链和框架包装，定位热点处图断、guard 失败与重编译原因；检查 shape、stride、dtype、实例属性、cache、hook 和 forward 替换等相关因素。区分首次编译、有限形状特化/动态化、持续重编译和有证据支持的 eager 回退；检查 `recompile_limit`、`accumulated_recompile_limit` 或该版本等价警告。图断不等于重编译，命中上限后的实际行为须按目标版本和运行证据判断。
3. **关联步号与影响。** 按 rank、函数/编译区域和 guard 原因整理事件，区分一次事件的多行日志与不同 rank 的重复记录，不把合并日志行数当作单 rank 重编译次数。结合现有或轻量采集的步号、时间戳及形状记录关联耗时尖峰；无法可靠关联时填“未知”，不强行归因。判断其影响属于启动成本、预热范围、关键路径或稳态性能；不要求消除全部图断，也不以没有警告证明零重编译或完整捕获。
4. **最小处理与回环。** 针对已确认的问题提出保持语义的最小处理，如修正包装位置、合理 eager 边界或有依据的形状策略。遵守关键决策询问规则，不通过关闭 cache、改变精度、放宽容差、提高重编译上限或静默回退掩盖问题。修复若改变编译边界、cache、精度或计算语义，视为新候选版本：获准后回到第三节，补充针对性测试，在新进程中重做正确性与本节诊断。一轮指实施代码或配置补丁并在新进程复测，最多 2 轮；只回到本节分析、未做修改的不计轮次。所有回环受累计预算约束。仍未解决则暂缓该候选并报告，记录剩余图断、重编译及限制。
5. **进入先导的准入条件。** 分两级：
   - **关键项**，任一项不满足或无法核实即暂停，不进入 4.2：目标路径在编译下执行；未命中重编译上限；正确性结论已通过；热点处图断已记录原因和可接受理由。
   - **非关键项**，明确记录后可进入 4.2，由先导补齐：后段形状覆盖；短训之后的重编译次数与步号；其他已列出的剩余问题。
6. **诊断交付。** 输出“位置/编译区域、rank 与步号、日志证据、原因、影响、处理建议、复测状态”的简洁表格，附日志/报告路径和复现命令。分列已确认、推断和未知项；仅有开关、安装日志或缓存文件不能证明完整捕获。诊断结果供 4.2 确定预热与形状覆盖，诊断日志耗时不作为正式性能数据。

### 4.2 先导运行与协议冻结

正式协议冻结前，安排不计入有效统计的先导运行，覆盖预期的预热与测量范围、代表性形状及状态变化，记录逐步耗时、编译/重编译触发步号与原因。先导采用拟定的正式配置，关闭数值检查等额外 hook，仅额外开启 `TORCH_LOGS=recompiles`，不开启 `TORCH_TRACE` 或 Profiler。recompiles 日志仍有开销，先导只用于确定覆盖范围与预热长度，不作为正式性能数据。先导必须在关闭检查的路径上核实目标确实被捕获、图数与重编译在 4.1 解释的范围内；与短训结论不一致时回到 4.1。固定种子不保证编译时序和步号完全复现，先导结果只用于设计和验证覆盖，不承诺后续不再重编译。

先导出现未解释的重编译或命中上限时，回到 4.1 分析；只有实施补丁才计入修复轮次。在已授权范围内，结合 4.1 与先导结果，按预先确认的规则选择预热长度和测量起点：应晚于已观察到的编译扰动并留余量，再检查耗时趋势。若始终无法达到稳态，报告未建立稳态，不无限延长。所有候选使用可比的输入覆盖和测量协议；改变原协议须新建版本，不能事后截取旧轮次冒充新协议数据。

### 4.3 稳态与统计协议

- 在正式测速前确定短任务的预热、测量步数、重复次数和稳态门槛。结合真实形状覆盖、重编译和窗口耗时趋势判定稳态，不能仅因完成固定预热步数就认定稳定；测量期发生显著编译扰动或命中重编译上限时标记无效，不临时删掉慢步。
- 进入正式测速前完成 4.1 的必要诊断和复测，记录可接受的剩余问题；未解决的捕获或稳态问题不能仅靠关闭诊断日志绕过。
- 正式测速关闭 Profiler、图断等诊断日志和额外数值扫描，两组保留相同轻量性能记录。正确性结论来自独立验证任务，测速不代替数值验收。
- 即使未设置 `TORCH_LOGS`，仍收集默认 stdout/stderr，扫描目标版本的 `recompile_limit`、`accumulated_recompile_limit` 及等价上限/回退警告，结合步耗时尖峰判断异常。无警告不等于零重编译；正式轮无法取得确切次数时填“未知”，不从尖峰数量反推次数。诊断与测速分别记录，不能用另一个进程的日志证明本轮没有重编译。
- baseline 与候选采用独立进程并重复测量；每个阶段安排前后 baseline 锚点（A-B-A，可共享相邻锚点），量化时段漂移，计入授权预算。若只能单次 baseline，明确无法估计其跨轮波动。小幅差异未超出测量波动或锚点漂移时结论为不确定；“两倍 CV”等只能作预先约定的筛查规则，不能替代置信区间或统计显著性分析。
- 各轮使用独立输出目录和独立编译缓存，记录冷／热缓存及其他相关缓存状态，不删除用户全局缓存。记录首步和进程总耗时，首步包含实际计算，不称为纯编译时间。
- 分布式记录全部 rank 的完整步数。若使用同步步墙钟，明确同步位置与额外开销；稳态全局吞吐可用 `有效全局 batch × 测量步数 / 最慢 rank 的完整测量窗口墙钟时间`，标明适用条件。逐步关键路径代理可取各 rank 步耗时最大值后计算中位数/P90，不与窗口总耗时混为一谈。
- 报告重复轮次的吞吐、步耗时分布与波动，记录各 rank 峰值 allocated/reserved 及是否包含预热。主机墙钟和设备事件耗时分列，不取最快 rank 代表全局。
- 有可比且稳定的数据时估算回本步数 `ceil(新增一次性成本 / 稳态平均每步节省)`；首步差作为成本代理时标为粗估。无稳态收益或数据不足时不计算有限回本步数。
- 记录 launcher 重试/恢复策略。发生重启时分别记录冷缓存和可复用缓存的启动成本，按预计启动次数估算总成本，不将自动重试拼接成一个无中断有效轮次。

### 4.4 编排自测与自动验收

多方案、多轮测试使用 manifest 驱动编排，记录候选、命令、预期配置/目标路径、协议、预算与来源。每轮独立目录及 `result.json`/`assessment.json`，拒绝覆盖历史 manifest；先导后的正式 manifest 单独生成并关联来源。复用轮次须验证证据，按索引引用或在允许时使用软链，不复制残留状态冒充新结果。

设备授权前完成 CPU 单测和 dry-run：验证参数解析到有效训练配置、各方案隔离、路径、源码哈希、端口选择、超时和清理范围，以及缺失 rank/步数和报告生成。必要时拦截模型构建/执行入口，保证 dry-run 不加载完整权重、不初始化加速设备。脚本修改后重新自测，不在设备窗口补做可前置的检查。

每轮自动校验有效配置、开关组合、实际目标路径与预期集合完全一致、各 rank 元数据一致及步数完整；无模型保存/无 Profiler 的测速任务还应检查对应产物不存在。配置与路径校验只是接入证据，不能替代捕获验证。失败则写入原因、保留结果，不纳入有效统计。

### 4.5 时间线与显存专项（按需）

按两种情况触发：
- **显存异常（随时）。** 正确性短训、先导或正式轮任一阶段出现 OOM 或显存异常时，先保留现场：日志、`max_memory_*`、出错步号与 rank。再在授权预算内单独运行，开启显存历史记录并采集快照，立即使用 `analyze-memory-snapshot` 诊断，不等测速结束。缺少快照则记录缺口，按预算和授权提出补采方案，不从普通日志推断已完成显存专项分析。
- **解释收益（正式测速后）。** 单独采集接入前后同设置、同阶段的代表性 Profiler Trace，尽量覆盖多个连续 active step，使用 `profile-model` 检查目标路径与时间线变化；必要时用已有 HTA 环境汇总与交叉检查。

专项任务不用于正式计时；`TORCH_TRACE` 是编译诊断数据，不替代 Profiler 时间线。

## 五、资源保护与续测

- 每组启动前重新核实设备可访问、占用和可取得的进程归属信息；检查标准与等待上限按已确认方案执行。资源无法核实或出现外部竞争时，不将 OOM、退化或波动归因于候选本身。
- 只清理本次启动的进程组及其 worker；launcher 退出后仍检查残留，不自动修复设备节点。预热选择按 4.2 的授权规则执行，正式协议冻结后不自行增加轮次或延长预热。
- 运行期间以进程完成通知和适度轻量监控为主，避免高频轮询设备或重复全量检查。
- 编译错误、数值异常、超时和资源干扰分别记录。保存失败及无效轮次的原始数据与原因，不反复重试掩盖问题；是否继续其他独立候选遵循预先确认的停止规则。
- 续测核实来源、源码和配置，明确复用哪些有效轮次、尚缺哪些项目。历史无效结果可列为诊断数据，但不能混入有效统计或用其他版本 baseline 计算收益。

# 正确性、性能和失败回退

先约定数值容差，再动代码。同步消除本身不应该改变任何数值结果，除非你同时改变了算法（比如把布尔索引换成固定形状加 mask，输出的张量形状可能变了，需要确认下游消费方式也跟着变）。

## 数值正确性

- 对比改写前后：相同权重、相同输入、相同随机状态，前向输出、loss、反向梯度逐位或在项目既有容差内一致。涉及 `.item()` 换成 `.reshape(())` 的改动，确认后续运算的 dtype 提升规则没有变化（零维张量和 Python scalar 在某些混合精度运算里的行为不完全相同）。
- 涉及布尔索引改写（P3）：覆盖全零、全一、单元素、边界值的 mask；确认梯度正确回传到被选中和未被选中的位置（未被选中的位置梯度应为零，不是未定义）。
- 涉及 varlen 参数自建（P4）：用显式断言（如 `torch._check`）声明前提，而不是静默假设；用与原封装路径完全一致的输入跑一遍，确认数值一致，再考虑绕开封装层。
- 涉及延迟读取指标（P5）：确认日志/checkpoint 选择逻辑消费的是"正确那一步"的值，不是提前或延后了一步却没人注意到。如果有"保存最佳 checkpoint"之类依赖当前 step 指标的逻辑，延迟读取可能需要相应调整判断时机。
- 涉及非阻塞拷贝（P8）：故意在拷贝完成前读取目标张量（比如去掉同步点做对照实验），应该能观察到数据错误或非确定性结果，用来确认"如果没有正确同步会出错"，再确认当前实现确实有正确同步。

## 分布式与 checkpoint

- DDP/FSDP/DeepSpeed：确认同步消除没有改变集合通信的调用顺序和次数（指标聚合的 all_reduce 次数应该和改写前逐步对应，只是合并了标量个数）；多 rank 场景下确认每个 rank 读到的延迟指标是同一步的（不要有的 rank 读到第 N 步、有的读到第 N+1 步）。
- checkpoint 保存/恢复：如果某个标量状态（如优化器 step 计数）的读取方式改变了，确认保存的 checkpoint 格式不变，恢复后状态和改写前恢复的状态一致。

## 性能验收

- 优先用 [Trace 中的同步证据](profiling.md) 确认改写前后同步事件的次数和耗时确实下降，而不是只看一次墙钟时间的差异。
- 多次测量报告中位数和离散程度；分别记录包含编译/预热的首次执行和稳态执行。
- 如果改写后墙钟时间没有变化：检查是不是这次同步原本就不在关键路径上（比如 GPU 本来就还有别的工作没做完，CPU 等待没有真正造成空闲）；检查非阻塞拷贝的源张量是否真的 pinned。
- 如果改写后出现新的性能问题（比如延迟读取的指标导致日志系统行为异常，或者固定形状加 mask 的方案比动态形状方案计算量更大）：这些是真实的权衡，应该如实记录，不要为了"证明同步消除有效"而隐藏。

## 不支持或收益不明显时的回退

- 保留开关，关闭后能完全恢复到改写前的代码路径和数值行为。
- 明确报告：静态扫描只给出候选，没有 trace 的情况下不要宣称"已验证消除了同步"，应该写"候选，待用 trace 验证"。
- 没有目标设备、没有 trace 采集条件时，完成静态分析和代码准备即可，在交付物里清楚标注"未运行、未验证"，不要替用户下运行时结论。

# 同步消除模式

以下模式按"改什么、前提是什么、怎么验证"组织。每条都来自对 TurboPhysAI 六个模型和 GR00T 的真实源码阅读（见 [TurboPhysAI 跨模型证据](turbophysai-sync-evidence.md)），不含性能数字；收益必须在目标项目重新测量。

## P1 标量留在设备上

**现象**：对张量调用 `.item()`、`int(x)`、`float(x)`、`bool(x)`，或在张量上写 `if x:`，把值读到 Python 侧再继续计算或分支。

**改法**：
- 如果后续只是另一个张量运算的输入（如归一化因子、clamp 下限），保留零维张量，用 `.reshape(())` 代替 `.item()`。
- 如果是用来做分支（"这批里有没有正样本""要不要跳过这层"），看能否用 `torch.where`、掩码乘法、或者始终执行两个分支再按掩码选择结果来替代。
- 如果必须读到 Python 侧（如写 JSON 日志、提前停止训练循环），看能否合并多个标量一次性读取，并延迟到下一步开始前（见 P5）。

**不适用**：真正需要立即、同步地在 Python 侧做决策时（如用 loss 是否为 NaN 来决定是否中止训练并保存 checkpoint），消除同步可能让错误延迟暴露；需要权衡。

**验证**：改前改后数值逐位一致（零维张量和 Python float 参与后续计算的结果应一致，注意 dtype 提升规则）；确认改写后真的不再出现对应的 `.item()` 调用（grep 或 trace 均可）。

## P2 CPU 元数据不要来回搬

**现象**：一批数据里本来就是整数或小规模的元数据（图像尺寸、序列长度、mask 的有效长度），被整批一起 `.to(device)`，之后又要 `.item()`/`.tolist()` 读回来用。

**改法**：在搬运边界把这类字段单独处理，继续留在 CPU；只搬真正要参与设备端计算的张量。需要精确匹配原调用的参数签名和返回类型，否则会影响其他不相关的调用点。

**前提**：该元数据在源头确实是 CPU 侧产生的（比如 dataloader collate 时的 Python int/list），不是设备计算的中间结果。

**验证**：确认被拦截的调用形状和原函数在"不满足拦截条件"时完全一致（同样的 `kwargs` 透传）；用一个同时包含该字段和普通张量的输入跑一遍，检查普通张量仍然正确搬到目标设备。

## P3 布尔掩码索引换成固定形状操作

**现象**：`tensor[bool_mask]`、依赖 `nonzero()` 输出长度分配后续张量、或者先 `cat`/`stack` 再按条件筛选。这类操作的输出形状由数据内容决定，框架常需要先知道非零元素个数（一次同步）才能分配输出。

**改法**：
- 用 `torch.where(cond, a, b)` 替代"选中为 a，否则为 b"的掩码赋值。
- 已知上界时，用固定大小的输出缓冲区 + 有效长度 mask，而不是动态长度的筛选结果。
- 需要索引时，用 `torch.nonzero(...).flatten()` 得到索引后接 `index_select`/`index_copy_`，而不是直接布尔索引（注意 `nonzero` 本身如果后续不依赖其长度做分配，通常不会强制同步，关键是"索引之后的操作是否依赖动态形状"）。

**前提**：下游消费者能接受固定形状加 mask 的数据表示（例如注意力机制通常本来就要处理 padding mask）。

**验证**：确认掩码边界情况（全零、全一、单元素）下形状和数值正确；检查梯度是否正确回传到被选中和未被选中的位置。

## P4 varlen API 自己构造长度参数

**现象**：调用某个高层 attention/kernel 封装时，封装内部从 `seqlens` 张量算 `max_seqlen = seqlens.max().item()` 再传给底层实现；或者需要从长度张量推导 `cu_seqlens`。

**改法**：如果调用方已经知道序列的组织方式（例如单样本打包、固定分桶上界），绕开封装层直接构造 `cu_seqlens`/`max_seqlen` 作为编译期常量或预分配张量，自己调底层实现。

**前提**：这类改写通常绑定很强的假设（batch=1、打包后的序列、已知上界），迁移到其他调用场景前必须重新核实这些假设是否成立，否则结果会错，不只是变慢。

**验证**：用 `torch._check` 或等价断言显式声明假设（如长度大于零），而不是静默假设成立；对照原封装的输出数值逐位一致。

## P5 指标合并、延迟读取

**现象**：训练循环每步对 loss、grad_norm 等分别调用 `.item()` 来打日志或做提前停止判断，每次调用都是一次独立的阻塞同步。

**改法**：
- 把多个标量 stack 成一个张量，做一次分布式归约、一次 `.cpu().tolist()`，取代多次单独读取。
- 更进一步：把结果拷到 pinned host memory，用 `cuda.Event` 记录，训练循环继续往前跑，下一步开始前才 `event.synchronize()` 读取上一步的值。这样 GPU 队列不会在读取点等待。

**前提**："延迟一步读取"要求训练逻辑不依赖该值的即时性（例如不是用本步 loss 来决定本步是否跳过优化器更新）；pinned memory 的拷贝目标必须真的是 `pin_memory=True` 分配的，否则 `non_blocking=True` 不会真正异步。

**验证**：核对延迟读取后，日志里记录的是"上一步"还是"这一步"的值，文档和下游消费者（如 best-checkpoint 判断）要用对应语义；确认关闭该优化后能完全恢复到逐步同步读取的行为，方便 A/B。

## P6 关掉库内部默认的同步

**现象**：某些框架/工具默认在每步调用一次 `cuda.synchronize()` 或等价操作，通常用于计时或诊断，和训练逻辑本身无关（例如 DeepSpeed 的 throughput timer）。

**改法**：找到对应配置开关关闭即可，通常是框架自带的选项，不需要改模型代码。

**前提**：确认关闭后不影响依赖该同步的其他功能（例如某些基于同步时间点的性能剖析或 OOM 检测逻辑）。

**验证**：关闭前后功能行为（除了被关闭的计时/诊断输出）应完全一致；检查是否有其他代码隐式依赖这个同步点作为"安全点"（比如在这之后才认为可以安全释放某些 buffer）。

## P7 必须留在 CPU 的求解，收敛成一次 D2H/H2D

**现象**：某些算法（典型是匈牙利匹配 `scipy.optimize.linear_sum_assignment`）只有 CPU 实现，必须把输入搬到 CPU、算完再搬回 GPU。

**改法**：确保整个输入只做一次 `.detach().cpu()`，结果只做一次 `torch.from_numpy(...).to(device)`，而不是在函数内部对矩阵的某些元素再零散读取或写入。这不是"消除"同步，是把本来可能多次的同步收敛成一次。

**前提**：这类必要的 D2H 通常规模较小（匹配问题的矩阵尺寸），如果规模变大需要重新评估是否值得搬到 CPU。

**验证**：确认该函数被调用的频率（每个样本一次，还是每层一次），以及是否处于 `torch.compile` 的编译区域内——如果在编译区域内，需要用 graph break 或者把这段隔离到编译边界之外。

## P8 非阻塞拷贝的两个必要条件

**现象**：代码里出现 `tensor.to(device, non_blocking=True)`，但没有确认源张量是否 pinned，也没有确认消费点是否等待。

**改法/检查清单**：
1. 源张量必须是 `pin_memory()` 分配的 CPU 张量，否则 `non_blocking=True` 不报错但也不会真正异步。
2. 拷贝发起后，必须在真正消费数据之前有某种同步点：显式 `event.synchronize()`、`stream.synchronize()`，或者默认 stream 上后续操作的隐式串行化。如果拷贝发生在非默认 stream，还需要 `record_stream` 防止 pinned buffer 被过早复用。

**验证**："改了但没变快"排查源张量是否真的 pinned；"变快了但偶尔结果错"排查是否读到了尚未完成拷贝的数据，尤其是多个 stream 交替使用同一块 host/device buffer 的场景。

## 不适用的场景（通用）

- 本来就在 CPU 上跑、且后续也不需要上设备的纯数据预处理逻辑；消除这类"同步"没有意义，因为它从来不涉及 GPU 队列。
- 已经在 `torch.compile` 捕获的区域内：那里的 `.item()`/动态分支通常直接导致图中断或报错，优先交给图中断诊断处理，而不是本 skill 的模式。
- 把本应同步暴露的错误（如梯度里的 NaN/Inf 检测）悄悄变成异步，导致问题延迟到后面才被发现——这类"消除"要和训练正确性的权衡一起讨论，不能默认是纯收益。

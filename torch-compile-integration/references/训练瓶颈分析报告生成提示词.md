# 训练瓶颈分析报告生成提示词

使用 `$torch-compile-integration` 对当前 PyTorch 训练项目开展瓶颈诊断，结合 Profiler Trace、HTA 和实际源码，生成一份以表格为主、证据可追溯的瓶颈分析与 `torch.compile` 建议报告。

关键决策使用 `$grill-me` 与我确认。先自行核实源码、配置和日志中能够查明的信息，再集中询问缺失输入或需要我选择的方案。本轮以分析和报告编写为主，编译接入与优化实施留待后续。

## 输入

- 项目路径：【路径】
- 训练命令或配置：【未知则从项目中查找】
- 训练 Python 环境：【未知则核实当前环境】
- Profiler Trace：【同一次运行的 Trace 文件或各 rank 目录】
- HTA 分析环境：【安装 HTA 的 Python 环境】
- 显存快照、图断日志或 tlparse 报告（可选）：【路径】
- 优化前后两组数据（可选）：【路径及对应配置】
- 输出目录：【路径；未指定时创建独立的带时间戳目录】

允许执行 CPU 分析，并在输出目录保存报告、CSV、分析脚本和输入索引。原始 Trace 保持只读。

## 分析流程

1. **核实环境与数据。** 读取项目 `AGENTS.md`、训练入口、有效配置和日志，核实实际模型结构、训练调用链及已有编译范围；记录代码版本、环境和采集配置。检查 Trace 来源、rank、有效 step 和设备事件，并验证 HTA 能否导入和解析。
2. **使用 `profile-model` 概览瓶颈。** 检查 CPU/GPU 算子、kernel、设备活动空档、搬运、同步、通信和 rank 差异，再选择代表性 rank、慢 rank 及训练阶段深入分析，说明选择依据。
3. **使用 HTA 复核。** 分析 temporal breakdown、GPU kernel breakdown 和 idle-time breakdown；多卡任务增加通信计算重叠与 rank 差异分析。保存关键 CSV，环境支持时导出图表。若有优化前后两组数据，先核对配置和口径再比较。
4. **按输入开展专项分析。** 有显存快照时使用 `analyze-memory-snapshot`；有图断日志或 tlparse 报告时使用 `debug-graph-breaks`。缺少数据时明确标记未分析。
5. **结合源码评估 Compile 候选。** 按热点和真实调用链比较整模型、训练步骤、子模块及局部 Tensor 计算边界。沿用 Skill 的候选表和 A/B/C/D 分类，列出源码位置、实例范围、热点证据、接入位置、初始配置、风险与验证方法。实验优先级不代表已证实的收益排名。
6. **给出首选方案与后续清单。** 推荐一个首选 Compile 方案及适用的替代边界；验证计划覆盖输出、loss、梯度、参数更新、数值有限性、保存重载、首次调用成本、稳态吞吐与峰值显存。其他瓶颈单独列入后续事项。

## 执行与结论边界

- 明确时间窗口、单位和百分比分母，区分主机墙钟、kernel 累计时长和包含 kernel、memcpy、memset 的设备活动并集；保留异步阶段归属限制。原始事件空档与 HTA idle 分列，`non_compute_time` 不称为 idle，kernel 时间占比不称为硬件利用率。
- 区分实测、源码确认和推断；小 kernel 多、同步阻塞或窗口差值仅作为线索。Profiler/HTA 用于诊断，正式测速另行设计，不承诺未经验证的加速。
- HTA 缺失或不兼容时逐项记录失败和警告，继续可做的 Trace 与源码分析。缺少协作 Skill 时按 `$torch-compile-integration` 的规则按需获取、校验和读取，无法获取时使用包内流程并注明限制。
- 补采、修改源码、安装运行依赖或执行编译实验前，先给出具体方案并与我确认。补采方案包括目的、命令、卡数、batch、步数、采样设置、时间预算、资源检查和停止条件；优先使用已有采集入口或不改源码的外部包装。默认不建立 Parquet 缓存。

## 报告结构与交付

生成 `<项目名>_training_trace_compile_analysis.md`，按“总览表 → 逐项证据 → Compile 建议 → 验证与后续工作”组织，保留以下 0–7 章：

| 章节 | 内容与组织方式 |
| --- | --- |
| 0. 摘要 | 用“结论、关键证据”表概括主要发现、量化依据和首选候选，标明推断与限制。 |
| 1. 环境、配置与数据口径 | 用表记录硬件、软件、实际训练配置、可训练部分、Trace 和分析范围；另列实际模型部件、数量及依据，说明时间口径、HTA 独立口径与采集限制。 |
| 2. 主要瓶颈及证据 | 先给“类别、对应小节、量化证据、候选方向”总表；2.1 展示代表性 step 的阶段分解，后续小节按实际证据分析通信、主机等待、搬运、计算热点、已有编译及数据加载。 |
| 3. 建议编译的位置 | 按 Skill 的候选表列出实验顺序、源码符号与实例范围、分类、依据、编译边界、接入位置及风险；说明候选间的包含或互斥关系、已有包装和排除理由。窗口差值仅用于筛选。 |
| 4. 推荐范围、初始配置与验证 | 分“推荐范围、初始配置、验证计划”说明首选与替代边界、版本适用的参数和生命周期入口，以及正确性、捕获、重编译、冷启动、稳态性能和显存的最小对照协议。 |
| 5. 当前不优先通过 Compile 处理的路径 | 用“位置、开销与证据、当前判断、后续方向、风险”表整理其他瓶颈，说明暂不优先的理由，不作永久不可编译的判断。 |
| 6. 证据等级与未验证项 | 用“证据类型、具体结论及来源”表分别记录 Trace 实测、HTA 汇总、源码确认、推断和未验证项，说明缺口如何限制结论。 |
| 7. 后续建议（本次不执行） | 按依赖关系和优先级列出补采、Compile 对照及其他专项任务，说明目的、输入和完成标准；附产物索引与复算命令。 |

第 2 章的阶段表应包含阶段、时间范围、窗口时长、计算与通信、kernel 数及候选判断，并保留未归类区间；后续小节按“量化观察 → 源码调用链 → 可能机制 → 结论与限制”展开。模块划分和小节数量随项目调整，不照搬其他模型。

保存关键 CSV、可生成的图表、分析日志、实际使用的复算脚本和输入索引；脚本支持重新指定输入与输出，不覆盖历史结果。交付前核对表格计算、单位、分母、源码引用及前后结论。没有实际编译对照时，明确标注：**编译建议尚未验证收益**。

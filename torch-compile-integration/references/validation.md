# 正确性与性能验证

重复层/嵌套编译需区分包装创建、实际图数及运行命中，检查不同 driver/模块类型/输入和缓存归属。动态标记覆盖 None、0/1、已标记轴及 eager 输出传递；compile 与 checkpoint 组合需真实验证重算的外层引用、Tensor 副作用、梯度和参数更新，控制替身不能证明正确性。配置冻结后改参数或关闭大块编译不保证卸载既有包装或关闭独立小函数入口，默认用独立进程对照。实例见 [OpenWAM](openwam-compile-case-study.md#最小验证与当前证据)。

按问题选择案例与最小验证见 [跨模型问题参考](compile-problem-patterns.md)。注册目标及别名覆盖不等于运行命中：尤其区分类/实例/方法包装和原函数/改写函数，确认全局关闭变量是否也控制显式 disable。用独立进程检查启停；同一类对象返回不证明先前编译已解除。分桶验收按实际预取/现场路径进行，保留有效长度，不把桶容量当有效元素数。

## 按需 AOT 与重编译适配验收

涉及局部 AOT 时，分别验证准备/导出、加载/权重绑定、实际命中和数值正确性。覆盖首次/连续片段、缓存重置和原地修改、尾块、非方形输入、支持的 batch/dtype/layout、未匹配变体、部分/全部准备失败与命中后执行异常。比较输出和缓存内容；导出成功或列表浅拷贝不证明数值和状态隔离。无梯度编码案例不能证明训练反向兼容。

分桶测试零、桶边界两侧、负值和超上限，保持真实长度及下游索引/偏移契约；形状断言覆盖不满足约束的处理。重新采集代表性 Trace/日志确认实际路径，普通 torch.compile 另统计重编译；不把 AOT 查表与 Dynamo 重编译混为一谈。准备阶段未做正确性检查时，必须单独执行验证，不能因加载成功宣称通过。

关闭/开启使用相同重构、布局和输入状态；确认 Group 关闭是否恢复了原项目已有 compile 入口。分别记录编译准备成本、命中覆盖率、局部稳态、端到端吞吐和峰值显存，正式测速与 profiler/诊断分离。不依靠共享目录中形状同名的包证明兼容性，不清除用户全局缓存。详见 [Cosmos3 案例](cosmos3-compile-case-study.md)。

本文是包内完整的基本验证规范，不以其他 Skill、原始流程文件或 MapTRv2 源码为硬依赖。协作项按主表触发时优先复用/主动获取；无法获取或应用时继续按本文验证。只有用户当前提供的目标项目才是验证对象；缺少项目输入时不以历史案例代替测试。没有可用 Python/PyTorch/GPU 时可做静态分析和验证计划，运行正确性与 GPU 性能标记为未运行；不自动安装环境。

若用户本轮只要求分析和验证计划，本文的模型运行/采集步骤只作为后续建议，不自动执行。可检查已有离线数据与报告本身；verification-before-completion的使用不能越过该任务边界。

## 公平比较

已有数据分析先核对采集/当前环境、源码和配置对应、rank运行归属、steps与时间窗口；保留原始数据，复用报告前核对来源有效性。HTA各API状态与指标口径见 [HTA参考](hta-analysis.md)，部分失败不得被其他成功项掩盖。

- 使用代表性小规模输入，记录 shape、stride、dtype、设备、训练/eval、AMP、batch 和序列长度分布；不要只测最规整尺寸。
- eager 与 compiled 使用相同起始参数、输入和相关状态。训练比较要恢复模型、优化器、梯度、buffer、随机状态和 scaler 等，不能依次训练同一个模型后比较不同状态。
- 沿用项目的精度要求或说明采用的容差。检查结构、shape、dtype、输出、NaN/Inf；训练还检查 loss、梯度与必要的参数更新。
- 随机算子可能因执行路径不同产生不同随机序列；既不强求所有路径逐位一致，也不直接忽略随机性。依据项目契约选择可复现局部测试或统计验证，不禁用 dropout 来冒充训练正确。
- 验证 compile 开关关闭路径；若修改 checkpoint 或包装逻辑，覆盖保存恢复、train/eval 切换等相关行为。

## 分开测量成本

1. 首次调用/冷启动：说明是否新进程、编译缓存是否已存在；首次调用通常包含实际执行，不把它全称为纯编译时间。不要删除用户全局缓存来制造冷启动。
2. 预热后稳态：先预热，再多次测量，报告样本数、中心趋势和波动。不同 shape 应覆盖各自的编译/预热。
3. 端到端：同时保留包含真实数据处理、必要通信等的业务指标，防止局部提速却整体无收益。
4. 内存：在一致的进程/缓存条件下记录 allocated、reserved 与适当的峰值指标；只重置峰值计数不会释放已有分配。不能把缓存残留算作某个方案独有成本。

GPU 异步执行不能用未经同步的 CPU 时间直接当 GPU 耗时。按测量目标使用设备同步后的墙钟时间或 GPU events，并说明范围；GPU events 不替代编译和完整 Python/IO 路径的端到端计时。性能测量与 profiler 采样分开，正式性能对照关闭Profiler、数值检查和诊断日志，正确性/诊断采集另行进行，避免相关开销污染基准。

不以CPU窗口减kernel累计时间定义GPU空闲，不把事件占比当SM利用率或把重叠事件累计为关键路径；每个关键数字给出窗口、分母、单位、rank/stream与样本范围，抽查原始时间线。区分原始Trace实测、HTA汇总、源码确认、推断与未验证项，不能将不同窗口差值写成compile收益。

报告 eager/compiled 的稳态时间、首次调用时间、峰值内存和变化。可估算回本迭代数：额外启动成本 / 每步节省时间；节省不为正时不报告回本。

## 诊断与停止条件

图中断处理按 [P4](compile-problem-patterns.md#p4) 选择保持语义的 Tensor 改写、边界调整或局部 eager；没有固定优先顺序。重编译转 P3，重复层/嵌套入口关联 P7；普通错误先调试，不用关闭编译掩盖。

必要时使用目标版本支持的 TORCH_LOGS graph_breaks/recompiles 或 TORCH_TRACE/tlparse。日志有图中断不等于必须消除所有中断；将其与实测影响联系起来。

确认实际调用了 compiled 路径，检查代表性变化是否造成持续重复编译。不要把 fullgraph 编译成功当作数值或性能验证。

修复验收分三项：①正确性——按项目容差检查输出及适用的 loss、梯度和状态；②捕获——用日志/Trace 确认预期编译/eager 边界及剩余图中断和重编译，不按重复日志行数推算图数；③性能——关闭 Profiler、诊断日志和额外检查后，对比首次调用、稳态耗时/吞吐、波动及峰值显存。三项分别写通过/失败/未运行，Profiler 不代替数值检查或正式计时。

按实际影响、证据与修改成本筛选；低影响、收益未超过波动或成本偏高的候选可记录原因后暂缓，不设通用百分比门槛。阻止目标捕获或影响正确性的问题单独处理。失败时先定位本轮最小改动，再按已约定策略修复、缩小边界或回退；使用适合的新进程复测，遵守任务预算和停止条件，不能无限重试或扩大范围。保留失败证据，不静默改变 fullgraph、删除必要行为、放宽容差或启用 suppress_errors。

先在用户允许的预算内执行有限候选比较。无 GPU 时不声称 GPU 性能通过；测试失败时先定位最小复现，不能通过放宽容差、改变输入语义或静默 eager fallback 掩盖问题。

## 验收用例建议

用小型实际项目做行为验收，避免只检查文案：

- **仅分析请求**：项目源码不变，输出具体文件/符号和编译候选，准确说明无 trace 的证据限制。
- **稳定模型的实施请求**：加入开关，eager/compiled 输出及适用的梯度满足项目容差，提供真实计时命令和数据。
- **包含 .item() 或数据相关分支**：指出具体问题，使用 debug-graph-breaks 或官方诊断，保持分支语义。
- **多种 batch/长度**：报告重编译行为，比较合理的边界/动态策略，不盲目固定 dynamic=True。
- **没有可用 GPU**：仍给出可执行方案和未验证清单，不编造速度与显存结果。

## 复杂项目的契约与归因验收

三组对照优先用于混合重构：A 原实现；B 重构后但编译关闭；C 相同重构且编译开启。A/B 衡量重构影响，B/C 衡量编译影响；缺少某组时说明结论限制。装饰器形式的现有代码应先设计该版本可验证的关闭路径，不能想当然认为某个全局环境变量禁用了全部编译。日志确认所有目标入口的实际执行路径。

冻结输入、精度/TF32策略、布局、通信、NUMA、数据加载、容器和后端配置。单机/多卡、训练/推理分别报告；推理 FPS 不能证明训练 iter 提速。DDP 比较需说明同步点与聚合方法，不能只取最快 rank。

| 场景 | 验收重点 |
| --- | --- |
| 固定循环、list/dict、多层预测 | 候选不能因语法被排除；跨层输出顺序、长度及梯度一致 |
| NumPy/PIL 随机增强 | eager 岛的随机性、概率、状态更新保持；不将其删除后计作 compile 收益 |
| CPU 匹配与设备往返 | 同一有效代价矩阵、标签/索引对应及返回对象正确，ties 按任务要求处理 |
| force_fp32/auto_fp16 包装 | 精度装饰器顺序、输入/中间 dtype、AMP、loss/梯度与溢出行为 |
| 可变 GT 与 padding | N=0/1/容量边界/超限；mask/length/索引映射一致，无虚假有效目标 |
| 原地操作、缓存/buffer | 输入副作用、alias、首次初始化与后续调用、train/eval 切换 |
| 父子都 compile | 实际捕获区域、子 mode 生效情况、重编译与边界碎片化成本 |
| 厂商与私有 options | 目标构建支持证据，禁用/启用对照，不向其他后端泛化 |

证据状态分开写：源码采用、用户报告有效、可关联日志支持、本次运行复测。每个性能数字附版本/输入/条件和日志位置。对于已有项目案例，没有实测时只接受“可追溯源码经验”，不能声称通过上述行为验收。

## 包装与开关的独立验收

- 建立目标符号→工厂→运行时条件→返回路径的映射；区分初始化关闭和启用后关闭。关闭后原路径可能没有 helper 重构/布局变化，这种 A/B 不能证明 compile 单项收益。
- 核对缺少 API、全局开关、Group 启用、独立 opt-in 的组合；单独写明显式关闭、能力不足和编译创建/首次调用失败，不能将未捕获异常视为自动回退。
- 用受控替身可以检验参数传递、返回 original、缓存命中/换 mode/复用和异常传播；只证明包装控制逻辑，不证明 Dynamo、后端、数值、内存或吞吐。替身不能代替真实 engine 的逐次分派验证。
- 缓存为全局状态时，测试环境要隔离和重置，不污染目标进程；实际应用还需测试用户真实调用顺序和多配置共存。
